# Позиции меню в заказе

Гость может добавлять позиции меню в свой заказ — как во время его создания, так и позже, пока заказ ещё открыт (не финальный). Позиции только **добавляются** — удалить или отменить уже добавленную позицию гость не может: это осознанное ограничение backend (роль `user` не имеет прав ни на `removeOrderItems`, ни на `updateOrderItemsStatus`), отменить ошибочную позицию может только персонал через свою панель.

## Точки входа

Три точки входа, два разных экрана:

1. **«меню»** на экране создания заказа (`lib/screens/order/new_order_screen.dart`, кнопка «Оформить заказ») — позиции собираются в локальную корзину **до** отправки заказа (см. «Корзина при создании заказа» ниже).
2. **«меню»** на экране заказа (`lib/screens/order/order_detail_screen.dart`, блок информации о заказе) — под списком текущих позиций и итоговой суммой.
3. **«Меню»** (иконка) на том же экране заказа — в панели ввода чата с заведением, рядом с полем сообщения.

Точки 2 и 3 ведут к одному и тому же обработчику `_addMenuItem()` в `order_detail_screen.dart` и видны только пока заказ ещё редактируемый — `Order.isEditable` (`lib/core/models/order.dart`) проверяет статус: `new`, `in_progress` или `calculation`. Для `completed`/`canceled*` кнопки скрыты — backend в любом случае отклонит `addOrderItems` для финального заказа.

Все три открывают один и тот же пикер меню (`showMenuItemPicker`, `lib/screens/table/menu_item_picker.dart` — тот же виджет, что и для дозаказа за столом), гость выбирает позицию и количество.

## Корзина при создании заказа

`addOrderItems` требует уже существующий `orderId`, поэтому передать позиции меню прямо в `createOrder` нельзя — контракт этой мутации не менялся и не должен. Вместо этого `new_order_screen.dart` ведёт локальную корзину (`List<MenuItemPickResult>`, только в памяти экрана):

- «меню» открывает пикер и добавляет выбранную позицию в корзину; повторный выбор той же позиции увеличивает количество, а не создаёт вторую строку.
- Каждую позицию в корзине можно убрать (✕) — это ещё не заказ, ограничение backend на удаление здесь не действует.
- По нажатию «Оформить заказ»: сначала обычный `createOrder` (как раньше, без изменений контракта), затем — если корзина не пуста — по одному вызову `addOrderItems` на каждую позицию корзины, используя уже полученный `orderId`. Итоговый `Order`, с которым гость попадает на экран заказа, собирается из ответов этих вызовов (`menuItems`/`hookahItems`/`subtotal`/`finalTotal`), а не остаётся пустым.
- Если часть позиций не добавилась (сетевая ошибка, отклонение backend) — заказ всё равно считается созданным (он уже есть на сервере), гость видит тост с именами позиций, которые не добавились, и попадает на экран заказа как обычно; отсутствующие позиции можно повторно добавить оттуда через точки входа 2/3.

## Что показывает экран

Блок информации о заказе (`_buildOrderInfo()`) отображает текущие `menuItems` и `hookahItems` заказа (название × количество, цена за единицу) и `finalTotal`. Список не рендерится вовсе, если позиций ещё нет — пустой заголовок не показывается.

Позиция, которую отменил персонал (`status: "canceled"`), не исчезает из списка — она остаётся видимой, но зачёркнута и помечена меткой «Отменено» (`_buildOrderItemRow()`). Это единственная разница в отображении между позициями со статусами `new` и `canceled`; безвозвратно удалённые персоналом позиции (`admin`) в списке уже не показываются — их просто нет в `menuItems`/`hookahItems`, которые приходят с сервера. Подробнее о том, откуда берутся эти изменения — раздел «Действия персонала» ниже.

Цена и списание/начисление баллов лояльности для дозаказанных позиций **не пересчитываются** — скидки и баллы применяются только при создании заказа, поэтому эти поля на экране дозаказа не показаны.

## GraphQL-контракт

`GQLMutations.addOrderItems` (`lib/core/graphql/mutations.dart`) вызывает мутацию с одним элементом списка `menuItems` на вызов (по числу позиций, которые можно выбрать в пикере за раз) — `hookahItems` этой фичей сознательно не передаётся, дозаказ кальяна через UI не реализован:

```graphql
mutation {
  addOrderItems(
    orderId: "..."
    loungeId: "..."
    menuItems: [{ menuItemId: "...", quantity: 1 }]
  ) {
    id
    status
    menuItems { id menuItemId name quantity unitPrice status }
    hookahItems { id name flavor quantity unitPrice status }
    subtotal
    finalTotal
  }
}
```

После успешного ответа экран обновляет `_order` **напрямую из ответа мутации** — никакого push/WS-уведомления о собственном добавлении гостю не приходит (соответствующее серверное событие адресовано только персоналу), это ожидаемое поведение backend, а не баг. `GQLQueries.orders` (`lib/core/graphql/queries.dart`) расширен теми же полями (`menuItems`, `hookahItems`, `subtotal`, `finalTotal`), поэтому список заказов и push-навигация (`lib/core/notifications/push_navigation.dart`) тоже видят актуальные позиции при обычной загрузке.

## Права доступа

- Добавлять позиции может только владелец заказа (JWT соответствует `userId` заказа).
- Добавление возможно только пока статус заказа `new`, `in_progress` или `calculation`.
- Никаких элементов управления для удаления/отмены позиций на экране гостя нет и не будет — у роли `user` просто нет соответствующих прав на backend.

## Действия персонала: подтверждение, отмена, удаление позиций

В отличие от добавления позиций (это делает только гость), состав и статус заказа могут в любой момент измениться **по инициативе персонала** (`staff`/`admin`/`owner`/`deputy` — у всех одинаковые права), без какого-либо действия со стороны гостя:

- **Подтверждение заказа** — персонал переводит заказ в `in_progress`.
- **Отмена всего заказа** — статус переходит в `canceled_by_staff` (уже поддерживаемый статус, см. `StatusHelper`, `lib/core/utils/status_helper.dart`).
- **Отмена отдельных позиций** — обратимо: позиция остаётся в `menuItems`/`hookahItems`, но получает `status: "canceled"` и перестаёт учитываться в `subtotal`/`finalTotal`. Персонал может позже восстановить её (`status: "new"`).
- **Удаление отдельных позиций** — безвозвратно, доступно только `admin`: позиция полностью пропадает из массива.

Ни на одно из этих действий гость не может повлиять и не должен ничего подтверждать — соответствующих элементов управления в клиенте нет и не будет (см. «Права доступа» выше).

### Системные сообщения в чате

Каждое из перечисленных действий (включая подтверждение заказа) автоматически создаёт обычное сообщение в чате заказа — `senderRole` отправителя один из `staff`/`admin`/`owner`/`deputy` (никогда `"user"`). Специальной обработки по типу сообщения не требуется: это доставляется тем же механизмом, что и обычный чат (`GQLQueries.messages`, глобальная подписка `newMessage` — см. «Подписка `newMessage`» ниже), и тем же push-каналом (`NotificationService.showChatMessage`, заголовок «Новое сообщение») — отдельного API или push-типа для этого нет.

Единый источник правды «это сообщение от персонала или от гостя» — `SenderRole.isStaff(senderRole)` (`lib/core/chat/sender_role.dart`, `senderRole != 'user'`). До его введения три места в коде (лента чата заказа, счётчик непрочитанных в списке заказов, бейджик новых сообщений) сравнивали роль по-разному, и одно из них пропускало push/бейджик для `admin`/`owner`/`deputy` — теперь все три используют один helper.

### Подписка `newMessage`

Реальное поле GraphQL-схемы бэкенда для realtime-сообщений — `newMessage`, **глобальное** (без аргумента `orderId`; фильтрация по получателю — на уровне WS-соединения на сервере, orderId приходит внутри самого payload). Изначально клиент подписывался на несуществующие поля `messageCreated`/`messageCreated(orderId: ...)`, из-за чего подписка систематически проваливалась на сервере и realtime для чата не работал вовсе — расхождение маскировалось 4-секундным поллингом на экране заказа и оставалось незамеченным в списке заказов (там поллинга не было).

Payload `newMessage` не содержит `id`/`createdAt` (бэкенд их не заполняет в этом событии) — поэтому подписка используется только как триггер рефетча `GQLQueries.messages`, а не как источник готовой модели `ChatMessage`. На экране списка заказов (`orders_screen.dart`) событие обновляет только счётчик непрочитанных (`UnreadState.onNewStaffMessage`); на экране заказа (`order_detail_screen.dart`) — фильтруется по `orderId == _order.id` и запускает `_fetchMessages()`.

### Перезапрос состояния заказа

Т.к. состав и сумма заказа могут измениться без явного ответа от мутации (в отличие от `addOrderItems`, где обновление приходит в ответе), `order_detail_screen.dart` перезапрашивает актуальный заказ (`_reloadOrderState()`, тот же `GQLQueries.orders` + `findOrderById`, что и при ошибках `addOrderItems`) при каждом новом сообщении от персонала:

- сразу — если сообщение пришло через подписку `newMessage` (для текущего заказа);
- либо на очередном тике 4-секундного поллинга чата — если сообщение не было доставлено подпиской (например, из-за реконнекта WebSocket).

Локально закэшированный список позиций поэтому не считается источником истины дольше, чем до следующего системного сообщения — экран всегда подтягивает актуальные `menuItems`/`hookahItems`/`status`/`subtotal`/`finalTotal` с сервера.

### Push-уведомление открывает заказ

С сообщениями персонала связан настоящий FCM-push (`eventType: "new_message"`, заголовок «Новое сообщение», текст `"Заказ #<id>: <текст>"` — готовые и локализованные сервером, клиент их не переформулирует), обрабатываемый так же, как push об изменении статуса заказа: `OrderPushPayload.tryParse()` (`lib/core/notifications/order_push_payload.dart`) распознаёт оба типа события по `eventType`, `PushService._handleForegroundMessage` показывает нужный локальный канал (`showChatMessage` для чата, `showOrderStatusPush` для статуса). WS-подписка `newMessage` больше не дублирует видимое уведомление сама — только обновляет бейджик непрочитанных, чтобы не показывать одно и то же сообщение дважды.

`NotificationService.showChatMessage()` передаёт `orderId` как `payload` уведомления — тап по push-уведомлению чата (в том числе по системному сообщению об отмене/удалении позиций) открывает соответствующий заказ через уже существующий `handleOrderPushTap`, как и для push-уведомлений об изменении статуса заказа.

## Обработка ошибок

`_handleAddOrderItemsError()` (`order_detail_screen.dart`) реагирует на текст ошибки от `addOrderItems`:

| Ошибка backend | Реакция UI |
|---|---|
| `order can no longer be modified once it is completed or canceled` | Тост «Заказ уже закрыт, дозаказ недоступен» + перезагрузка состояния заказа (кнопки скрываются сами) |
| `invalid orderId` / `invalid loungeId` | Тост с общим текстом (без технических деталей), полная ошибка уходит в лог как `ERROR` — это баг клиента, не пользователя |
| `forbidden: only the order owner can add items to this order`, `no valid items to add`, любая нераспознанная ошибка | Тост с текстом ошибки сервера + перезагрузка состояния заказа |
| `unauthorized: login required to add items to an order` | Отдельно не обрабатывается — общий `GraphQLClient` (`AuthState._buildClient`) уже форсирует logout при протухшем токене, вне зависимости от того, какой запрос его спровоцировал |

Перезагрузка состояния заказа переиспользует уже существующую чистую функцию `findOrderById` (`lib/core/notifications/push_navigation.dart`) — запрашивает `GQLQueries.orders` и ищет заказ по id, вместо дублирования этой логики.

Отправка сообщения в чат (`sendMessage`) обрабатывает ошибку по тому же принципу: `_send()` больше не очищает поле ввода до успешного результата мутации — при ошибке введённый текст остаётся в поле, показывается тост с текстом ошибки сервера, автоповтор не выполняется (только следующая ручная отправка).
