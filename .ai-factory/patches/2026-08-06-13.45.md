# registerUser (и любой GraphQL-запрос) мог падать по таймауту 5с, хотя реально выполнялся

**Дата:** 2026-08-06 13:45
**Файлы:** lib/core/auth/auth_state.dart, test/core/auth/auth_state_timeout_test.dart
**Severity:** medium

## Problem

После деплоя бэкенд-фикса (см. соседний репозиторий hookah_backend, коммит ddd6625 / тег v2.18.2) на экране регистрации всё ещё появлялась ошибка:

```
UnknownException(TimeoutException after 0:00:05.000000: No stream event, stack: )
```

При этом пользователь сообщил, что сама регистрация фактически проходила (аккаунт создавался) — ошибка была ложной.

## Root Cause

`AuthState._buildClient()` (`lib/core/auth/auth_state.dart`) создаёт единственный на всё приложение `GraphQLClient` без явного `queryRequestTimeout`. Пакет `graphql` (5.2.4) по умолчанию подставляет `Duration(seconds: 5)` (`graphql_client.dart:32`) и применяет его как `Stream.timeout()` к каждому запросу (`query_manager.dart:279-281`). Если ответ не пришёл за 5 секунд, стрим кидает `TimeoutException('No stream event', ...)` — именно этот текст и совпадает с ошибкой на скриншоте один в один.

5 секунд — слишком жёсткий таймаут для мобильной сети + мутации, которая на бэкенде делает два последовательных gRPC-вызова (`GetStaffByUserID` + `CreateStaff`) и подпись JWT. Особенно после свежего передеплоя/пересоздания контейнера `staff` (холодный старт, прогрев соединений) запрос легко мог занять больше 5 секунд, будучи при этом полностью успешным на сервере — клиент просто переставал ждать раньше, чем приходил ответ.

## Solution

Явно задал `queryRequestTimeout: const Duration(seconds: 20)` в конструкторе `GraphQLClient` внутри `_buildClient()`. Значение с запасом покрывает мобильную сеть + многошаговый бэкенд, не будучи бесконечным (запрос всё ещё не зависнет навечно при реальном обрыве соединения).

Regression-тест `test/core/auth/auth_state_timeout_test.dart` без сети и без `fakeAsync` — читает публичное поле `authState.gqlClient.value.queryManager.requestTimeout` сразу после конструирования `AuthState()` и проверяет, что оно `null` либо ≥ 15с. Подтверждено: FAIL (`0:00:05.000000`) на коде до фикса, PASS после.

## Prevention

- `GraphQLClient(...)` в приложении создаётся один раз в `AuthState._buildClient()` — при любых новых фичах, использующих `gqlClient`, задержку сети/бэкенда нужно проверять относительно этого общего таймаута, а не только конкретной фичи.
- Значения по умолчанию сторонних пакетов (особенно "тихие" вроде `queryRequestTimeout = const Duration(seconds: 5)`) стоит явно переопределять и документировать в коде — иначе баг всплывает только на реальном устройстве при реальной задержке сети, а не в тестах/эмуляторе на локалхосте.
- Текст `TimeoutException(..., "No stream event")` в логах/скриншотах клиента почти наверняка означает `Stream.timeout()` без `onTimeout` где-то в цепочке (в данном случае — в самом пакете `graphql`), а не серверную ошибку — стоит сразу проверять `queryRequestTimeout`/`requestTimeout`, прежде чем подозревать бэкенд.
