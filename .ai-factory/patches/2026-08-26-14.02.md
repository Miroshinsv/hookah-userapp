# Map markers lost the "connected lounge" opacity distinction

**Date:** 2026-08-26 14:02
**Files:** lib/core/graphql/queries.dart, lib/core/models/lounge.dart, lib/screens/map/map_screen.dart, test/lounges_page_test.dart
**Severity:** medium

## Problem

On the lounge map, all open lounges rendered fully opaque and all closed ones semi-transparent (`opacity: 0.6`), regardless of whether the lounge account was actually claimed/connected (`ownerUserId` set). Before a prior refactor, connected lounges were opaque and unclaimed ones were dimmed, independent of open/closed status — that distinction had silently disappeared.

## Root Cause

`feature-map-viewport-lounges` switched the map from the unfiltered `lounges` query (full `Lounge` model, includes `ownerUserId`) to the viewport-filtered `loungesPage` query (lightweight `LoungeMapItem` model). The plan for that migration explicitly assumed `ownerUserId` was unavailable on the lighter item ("that field no longer exists on this lightweight item") and rewrote the opacity rule to use `status == 'closed'` instead — without checking whether the field could simply be requested. It could: the backend's `loungesPage.items` resolver returns the exact same `loungeType` GraphQL object as the full `lounges` query (`gateway/internal/delivery/graphql/schema.go`), which does expose `ownerUserId` — the Flutter query builder just never selected it for `loungesPage`. The assumption from that migration plan was never independently verified against the backend schema.

## Solution

Added `ownerUserId` to `GQLQueries.loungesPage`'s selection set and to `LoungeMapItem`/`fromJson`, then restored the original rule in `_buildLoungePlacemark`: `opacity: isConnected ? 1.0 : 0.6` where `isConnected = (l.ownerUserId ?? '').isNotEmpty`, matching the pre-refactor behavior (`git show 920f5e8`). Added an `AppLogger.d` summary of connected/not-connected marker counts per map rebuild.

## Prevention

- When a plan asserts a GraphQL field "doesn't exist" or "isn't available" on a lighter/derived type, verify against the actual backend schema/type definition before designing around that assumption — a field missing from *a specific query's current selection set* is not the same as the field being absent from the underlying GraphQL type.
- When replacing one derived-state field with another as a UI-driving signal (here: `status` swapped in for `ownerUserId`-derived "connected"), treat it as a behavior change requiring explicit user sign-off, not a mechanical migration detail — the two concepts (open/closed vs. connected/unclaimed) are semantically unrelated even though both drove the same `opacity` property.
- A model-level regression test (`LoungeMapItem.fromJson` parses `ownerUserId`) now guards this specific field; consider a lint/checklist step for "does this migration preserve every field the old query selected" when swapping GraphQL query builders in future map/list refactors.
